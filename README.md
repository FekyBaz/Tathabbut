# Tathabbut (تثبّت)

**A privacy-conscious open-source text filter for social feeds.**

Tathabbut is a Chrome extension that locally hides text matching user-selected categories. The first target is Facebook (facebook.com hosts: www, web, m, and the bare apex). It never deletes posts or modifies Facebook data.

> **Hide locally. Explain clearly. Restore anytime.**

The Arabic name تثبّت conveys careful verification and avoiding hasty judgment. Respectful criticism is not a violation category. The initial classifier uses narrow, deterministic starter rules; it does not establish truth or intent. Misinformation filtering is not enabled by default because verification needs evidence and provenance.

## Current status

The repository contains the initial Chrome Manifest V3 extension, optional FastAPI endpoint, CI tests/build, and project privacy/security documents. This is an early MVP and the Facebook selectors/rules need broader manual and language-aware evaluation before everyday use.

## Get the extension

1. Open the latest successful [GitHub Actions workflow](https://github.com/FekyBaz/Tathabbut/actions/workflows/ci.yml).
2. Open its run and download the `tathabbut-chrome-extension` artifact.
3. Extract the ZIP to a folder.
4. Visit `chrome://extensions`, turn on **Developer mode**, click **Load unpacked**, and choose the extracted folder.

The artifact is created by CI after tests and package-layout checks pass.

## Develop in Brave (rebuild without re-downloading)

For day-to-day development, build from source and load the build output once. Brave keeps that same folder loaded, so after each rebuild you only click **Reload** — no ZIP download, extract, or re-adding the extension.

1. Build once from source:
   ```bash
   cd extension
   npm install
   npm run dev:build
   ```
2. In Brave, open `brave://extensions/`, enable **Developer mode**, click **Load unpacked**, and select the `extension/dist` folder of this repository (for example `E:\tathabbut\extension\dist`).
3. After editing source, rebuild:
   ```bash
   cd extension
   npm run dev:build
   ```
   On Windows you can instead run `extension\dev-build.cmd`, which does the same build and prints the folder to select.
4. Back in `brave://extensions/`, click **Reload** on the Tathabbut card (or press `Ctrl+R` there) and test the updated extension.

Notes:

- Always load the built `extension/dist` folder — never `extension` or `extension/src`. Those contain TypeScript that must be bundled first; `dist` is generated by the build and is git-ignored.
- `npm run dev:build` is an alias of `npm run build`, so it produces the exact production package, runs the `verify-dist` check, and keeps a single output directory (no dev/release drift).
- Troubleshooting: if Brave reports a missing or invalid manifest, confirm `extension/dist/manifest.json` exists and re-run `npm run dev:build`. If the build fails, read the `tsc` / `vite` / `verify-dist` output — `verify-dist` names the exact missing or invalid package file. `npm run dev:build` and `dev-build.cmd` exit non-zero on failure.

### Lifecycle diagnostics (development only)

To inspect the content script's cleanup paths (observer/listener teardown, `pagehide` handling, and work dropped after disposal), enable the opt-in lifecycle log. It is **off by default**, separate from the popup's `[Tathabbut debug]` channel, and only prints lifecycle events — never post text, author names, or URLs.

1. On a `facebook.com` page in Brave, open DevTools (F12) → **Console**.
2. Enable it for that origin, then reload so startup is captured:
   ```js
   localStorage.setItem("tathabbutLifecycleDebug", "1");
   location.reload();
   ```
3. Read entries prefixed with `[Tathabbut:Lifecycle]` in the same page Console (filter the console by that string). Events: `init`, `observer:observe`, `listeners:add`, `pagehide` (with `{ persisted }`), `pagehide:keep-alive`, `dispose`, and `guard:reject` (with `{ where }`).
4. Turn it off:
   ```js
   localStorage.removeItem("tathabbutLifecycleDebug");
   ```
   (or set it to `"0"`). The flag is read on each event, so a change also applies to events after it without a reload.

This shows which code paths ran; it does not prove the absence of leaks and does not prove real-browser bfcache behavior. A real `pagehide` only appears after an actual navigation away (e.g. a bfcache-eligible back/forward navigation).

If you see no `[Tathabbut:Lifecycle]` output: the flag is read from the **host page's** `localStorage` (content scripts and the page share one origin's web storage), and the content script only reads it **when the script (re)runs**. So (1) after `npm run dev:build`, click **Reload** on the Tathabbut card in `brave://extensions/` — reloading the Facebook tab alone keeps the previously loaded build; and (2) set the flag, then reload Facebook, and in DevTools make sure the Console shows **Info**-level messages (the logs use `console.info`) and that the context selector is set to the page, not a specific frame.

### Filtering diagnostics (development only)

`[Tathabbut debug]` is the existing opt-in channel (popup → **Diagnostics**; stored per device). It prints counts, lengths, fingerprints, and reasons only — never post text, author names, or URLs. Use it to locate the failing stage instead of guessing:

1. Rebuild and click **Reload** on the extension card, then reload Facebook.
2. Open the popup and enable **Diagnostics**.
3. In DevTools → **Console**, filter `[Tathabbut debug]`.

Events and how to read them:

- `scan {articles, areas, leaves, nativeTextLeaves, nativeTextNodes, f1Nodes, suppressed, insideExisting, desktopUnits, serverUnits, uniqueUnits, postUnits, commentUnits, replyUnits, unknownUnits, mixedSkipped, duplicateNested, duplicateCandidates}` — the startup/settings scan. `articles` is **startup-only**: Facebook hydrates the feed after `document_idle`, so it can be 0 while the observer later finds the feed. Desktop roles/test IDs provide post/comment/reply counts; mobile SSR leaves without those markers are counted as `unknownUnits`.
- `mutations {batches, affected, ...same counts}` — throttled (at most once per second) summary of observer-discovered subtrees. This is the path that normally finds a hydrated mobile feed.
- `candidate {via, kind, length, fingerprint}` — a new or changed unit sent to classification; `via` is `desktop` or `ssr`; `kind` is `post`, `comment`, `reply`, or `unknown`.
- `classify {mode, labels}` — `labels: 0` means the local rules matched nothing.
- `decision {decision, reason, via, kind, fingerprint, ...}` — `reason: "no-rule-match"` means classification ran but no rule matched; `decision: "hidden"` with `reason: "rule-match"` means the hide path ran; `decision: "hide-failed"` means the page rejected the DOM update and partial presentation was removed.
- `progress {evaluated, classified, shown, hidden, hideFailed, noRuleMatch, duplicates, lastReason}` — throttled aggregate totals after results settle; a trailing summary is emitted after a burst.

Quick triage:

| Symptom | Meaning |
| --- | --- |
| `scan.areas` is 0 while DevTools finds `[data-mcomponent="ServerTextArea"]` | the script saw no text components at that moment (usually pre-hydration) or a stale build is loaded — check `mutations` next, then reload the extension card |
| `suppressed` is non-zero | candidates were rejected as controls, editable fields, or hidden regions (`aria-hidden`, `[hidden]`, role=button/navigation/banner); the keys name the reason |
| `nativeTextLeaves` is 0 while `areas` > 0 | the `.native-text > span.f1` shape was not the selected leaf |
| `candidate` with `via:"ssr"` then `classify.labels: 0` / `decision.reason:"no-rule-match"` | discovery and hiding are fine; the visible text is outside the local rule set |
| `mixedSkipped` > 0 | one SSR leaf mixed its own text with a different nested text region; the nested region is processed separately and the mixed parent is intentionally not hidden |
| `duplicateNested` > 0 / `duplicateCandidates` > 0 | duplicate parent/child text was collapsed to one target, or the same element was seen through multiple selectors |
| `decision.decision:"hide-failed"` / `progress.hideFailed` > 0 | policy matched but the page rejected the DOM mutation; no partial blur or orphan control remains |

The popup's `articles` number comes from the single startup `scan()`; use the popup's evaluated/classified/hidden counts (or the console events) for the observer path.

Extraction strips UI-only labels (`See more`, `عرض المزيد`, reaction/reply controls, translations) from a cloned node before classification. It never mutates the live post to remove them. If a parent combines its own text with a different nested SSR text region (for example a comment and a reply in one `.native-text`), Tathabbut does not hide the parent; the nested region is processed independently and `mixedSkipped` records the limitation.

Extension:
```bash
cd extension
npm install
npm test
npm run build
```

API:
```bash
cd backend
python -m venv .venv
# Windows: .venv\\Scripts\\activate
# macOS/Linux: source .venv/bin/activate
pip install -e ".[dev]"
uvicorn tathabbut_api.main:app --reload
```

Health check: `http://127.0.0.1:8000/health`.

## Categories in the starter
- Personal insults / harassment
- Hateful or dehumanizing attacks
- Threats of violence
- Spam

User controls include enabling/disabling filtering, selecting categories, adjusting confidence threshold, and optionally configuring a self-hosted API URL. Leaving the API blank keeps classification local. Remote calls are routed through the extension service worker; the extension requests optional access to the configured host only after the user saves that URL. HTTPS is required for non-local hosts, and changing or clearing the URL removes the previous host permission.

## Privacy and limitations
Provider keys must stay on the backend, never in extension code. Only a selected text snippet and chosen categories should be sent when remote classification is explicitly configured. The backend starter makes no external model calls.

Context matters: quotations, satire, reclaimed language, dialect, counterspeech, or reporting abuse can be misread by classifiers. Filtering is reversible and does not report or delete content. See [privacy](docs/PRIVACY.md), [responsible filtering](docs/RESPONSIBLE_FILTERING.md), and [threat model](docs/THREAT_MODEL.md).
